# 스펙 관리 구현 및 실행 안내

작성일: 2026-10-12

## 적용 범위

- 자격증·어학·학력·수상·프로젝트·실무·대외활동·교육의 8종 등록·수정·삭제 API와 Flutter 입력 흐름을 연결했다.
- 테스트 버전의 모든 사용자 입력은 선택이다. 유형과 소유 사용자, 고유 ID는 시스템 정보로 관리한다.
- 자격증 공식 검색과 직접 입력을 지원한다. 직접 입력 내역은 공용 자격증 목록에 추가하지 않는다.
- 내 스펙의 분류별 목록과 등록 건수는 실제 저장 내역으로 갱신한다. 완성도 100%나 공식 인증을 임의로 표시하지 않는다.
- 로그인·회원가입에서 JWT를 발급한다. 개인 데이터는 토큰으로 식별하며 `x-user-id`만으로 접근할 수 없다.
- 로그인 만료·로그아웃·계정 변경 시 기존 보호 화면을 닫는다. 토큰 갱신과 로그인 복원은 2026-10-17 후속 작업에서 추가했으며, 비밀번호 재설정 메일 발송은 아직 포함하지 않았다.
- 타이머는 스펙이 없어도 자유 학습을 저장할 수 있고, 등록한 스펙에 선택적으로 연결할 수 있다.
- 등록·삭제 시 타이머 선택 목록을 갱신한다. 삭제한 스펙의 연결 학습 기록도 삭제하고 다른 스펙·자유 학습 기록은 유지한다.
- 기존 60분 제한과 최근 기록 5개 저장 정책은 유지했다. 오늘의 학습 날짜는 서버 환경과 관계없이 한국 시간으로 계산한다.

## 저장 구조

`public.user_specs`는 사용자·유형·제목·타임스탬프와 검증된 유형별 `jsonb` 입력을 저장한다. 공식 자격증 연결은 선택이며, 인증 상태는 첫 버전에서 미검증이다.

- `POST /specs`: 새 내역 생성. 빈 입력도 별도 고유 ID로 저장하며 기존 내역을 덮어쓰지 않는다.
- `GET /specs`: 내 목록 조회. 유형 및 페이지 범위를 지정할 수 있다.
- `GET /specs/summary`: 사용자별 전체·대분류·세부유형 건수 조회.
- `GET /specs/:id`: 내 내역 조회.
- `PATCH /specs/:id`: 내 내역 수정. 미전달 값은 유지하고 명시적인 빈 값·`null`은 지운다. 유형은 바꾸지 않는다.
- `DELETE /specs/:id`: 내 내역 및 연결된 학습 기록 삭제.
- `POST /study-sessions`: `specId`를 전달하면 해당 사용자 스펙에 연결하고, 생략하면 자유 학습으로 저장한다.

모든 개인 API에 `Authorization: Bearer <accessToken>`이 필요하다. 다른 사용자의 스펙 조회·수정·삭제 및 학습 연결은 허용하지 않는다.

## 로컬 DB 적용

현재 `server/.env`의 연결 대상이 로컬 `specmoa_DB`인 것을 확인한 뒤 백업하고 마이그레이션을 적용했다. Supabase·Render·GitHub·기존 APK 배포는 변경하지 않았다.

백업: `db/specmoa_before_specs_20261012_1791799982389.dump`

마이그레이션: `server/src/database/migrations/1791763200000-AddUserSpecs.ts`

이관은 취득 완료 자격증만 새 내역으로 복사한다. 기존 `user_certifications`의 준비·보관 내역과 메모는 원본 테이블에 남긴다. 기존 학습 기록의 연결은 소유자·종목으로 하나의 스펙을 확정할 수 있을 때만 이관한다. 모호한 연결을 임의로 지정하지 않는다.

사용자 데이터가 들어간 테이블을 자동으로 삭제하는 롤백은 제공하지 않는다. 복원이 필요하면 백업을 확인한 후 별도의 복원 DB에서 검증한다.

## 실행

서버는 Node.js 22.x 설정을 유지한다. 이번 로컬 도구 실행은 Node.js 24.14.0에서 검증했다.

서버 터미널:

```powershell
cd C:\app_project\server
npm ci --include=dev
$env:DB_SYNC = 'false'
$env:PORT = '3101'
npm run start:dev
```

Flutter 터미널:

```powershell
cd C:\app_project\ui
flutter pub get
flutter run -d chrome --dart-define=API_BASE_URL=http://127.0.0.1:3101
```

기존에 실행 중인 서버가 있다면 같은 포트에 중복 실행하지 않는다. 개발용 JWT 비밀값이 없으면 서버 시작마다 새 서명 키를 사용한다. 기존 접근 토큰은 무효가 되지만, 2026-10-17 이후 발급한 유효한 갱신 세션은 DB가 보존되어 있으면 접근 토큰을 다시 발급받을 수 있다. `server/.env`의 `JWT_SECRET`에는 비공개 난수 32자 이상을 지정하는 것을 권장한다. 운영에서는 반드시 고정된 비공개 값을 설정한다.

새 모델·인증 구조가 추가되었으므로 기존 실행 앱은 한 번 완전히 재시작한다. 이후 목록 갱신은 화면의 새로고침과 등록·수정·삭제 후 갱신으로 처리한다.

## 배포 전 작업

1. Supabase DB를 별도로 백업하고 새 마이그레이션을 적용한다. `DB_SYNC=true`로 운영 테이블을 변경하지 않는다.
2. Render에 `JWT_SECRET`을 설정한다. `render.yaml`에는 신규 비밀값 생성 설정을 추가했으며 기존 서비스에 실제 적용됐는지는 배포 설정에서 확인해야 한다.
3. 서버를 재배포한 뒤 로그인·스펙 API·학습 기록 저장을 확인한다.
4. 새 서버와 함께 토큰을 전송하는 Flutter 앱을 다시 빌드한다. 이전 APK는 사용자 ID 헤더만 사용하므로 새 인증 서버와 호환되지 않는다.

프로토타입 인증을 정식 운영용으로 완성했다고 간주하지 않는다. 토큰 갱신·현재 세션 폐기는 2026-10-17에 추가했다. 로그인 요청 제한, 비밀번호 재설정 메일, 관리자 동기화 권한과 의존성 보안 업데이트는 배포 전에 별도로 점검한다. 비파괴적 `npm audit fix`는 적용했지만 메이저 업그레이드가 필요한 기존 NestJS 의존성 경고는 남아 있다.

## 2026-10-16 후속 안정화

화면 배치와 입력 항목은 유지하고 타이머·자격증 자동완성의 비동기 상태 처리를 수정했다. 새로운 화면이나 UI 컴포넌트는 만들지 않았다.

- 타이머 새로고침 중에도 마지막으로 확인한 목록·기록과 실행 중인 조작부를 유지한다. 갱신 실패 시 기존 타이머를 계속 조작할 수 있고 실패 메시지를 표시한다.
- 오래된 조회 응답이 최신 스펙 선택이나 실행 중인 시간을 초기화하지 못하도록 조회 순서를 확인한다.
- 사용자 변경 시 이전 선택과 화면 데이터를 비우고, 이전 사용자의 저장 성공·실패 응답이 새 사용자의 타이머나 메시지에 영향을 주지 않게 한다.
- 선택한 스펙이 실제로 삭제되면 해당 타이머를 초기화한다. 자유 학습은 다른 스펙의 등록·삭제에 영향을 받지 않는다.
- 학습 저장 실패 시 시간과 연결 스펙을 유지하여 재시도할 수 있다. 기존 60분 제한과 최근 학습 기록 5개 정책은 변경하지 않았다.
- 자격증 검색어를 수정하면 이전 자동완성 결과를 즉시 비운다. 명칭을 수정하지 않고 공식 검색 버튼만 눌렀을 때는 기존 공식 자격증 연결을 보존한다.
- 최종 저장을 시작하면 대기 중 검색을 취소하고 늦게 도착한 자동완성 응답을 무시한다.

## 2026-10-17 로그인 세션 보강

- 접근 토큰은 15분, 로그인 세션은 최초 발급부터 최대 30일이다. 갱신이 성공해도 30일 만료일을 연장하지 않는다.
- 서버 `auth_sessions`에는 갱신 토큰의 SHA-256 해시만 저장한다. 접근 토큰의 사용자와 세션을 함께 검증하여 로그아웃·만료된 세션의 기존 접근 토큰도 차단한다.
- `POST /auth/refresh`는 갱신 토큰을 교체한다. DB 행 잠금으로 동시 재사용을 차단하며, 이미 소비한 토큰은 다시 사용할 수 없다. `POST /auth/logout`은 현재 세션을 폐기하고 다른 기기의 세션은 유지한다.
- Flutter는 갱신 토큰만 `flutter_secure_storage`에 저장한다. 앱 시작 시 서버에서 사용자 정보를 다시 확인한 뒤 보호 화면을 연다. 접근 토큰·비밀번호·스펙 목록은 이 저장소에 보관하지 않는다.
- 인증 실패 요청은 갱신 후 한 번만 재전송한다. 여러 요청은 한 번의 갱신을 공유하고, 일시적인 서버 장애는 기존 로그인 정보를 지우지 않는다.
- 계정 변경 이후 이전 응답·늦은 토큰 갱신이 새 사용자에게 적용되지 않도록 차단한다. 로그아웃과 빠른 계정 변경 모두 이전 보호 경로를 닫는다.
- 새 화면이나 입력칸을 만들지 않았다. 로그인 버튼·회원가입 흐름·기존 로그아웃 메뉴를 재사용하고, 복원 대기에는 기존 로딩 표시를 사용한다.

주의 및 남은 범위:

- 이번 변경 이전의 세션 ID 없는 JWT는 호환하지 않는다. 새 서버·앱으로 함께 업데이트하고 처음 한 번 다시 로그인한다.
- 운영 배포 전에 두 마이그레이션을 적용하고 `DB_SYNC=false`를 유지한다. 로그인 응답에 갱신 토큰이 없는 구형 서버와 새 앱은 호환되지 않는다.
- 오프라인 로그아웃은 앱의 인증 정보부터 제거한다. 서버 세션 폐기는 네트워크 연결이 있어야 확인할 수 있으며, 원격 폐기 요청 실패 시 서버 세션은 원래 만료일까지 남을 수 있다.
- 단일 앱 인스턴스 내 동시 갱신을 처리했다. 동일 브라우저의 여러 탭 간 갱신 조정, 전체 기기 로그아웃·세션 관리 UI, 만료 세션 자동 정리는 별도 범위다.
- 갱신 응답을 받기 전에 연결이 끊기면 이전 토큰이 이미 소비됐을 수 있어 재로그인이 필요할 수 있다.
- 웹 보안 저장소는 HTTPS 또는 localhost 보안 컨텍스트가 필요하며, 모바일 Keychain/Keystore와 동일한 보호 수준으로 간주하지 않는다. 운영 웹 배포 시 XSS/CSP 및 쿠키 기반 세션 방식을 별도로 검토한다.
- `flutter pub get`은 패키지를 받았으나 Windows의 심볼릭 링크 단계에서 개발자 모드 활성화를 요구했다. 웹 release 빌드와 `--no-pub` 테스트는 통과했으며, Android 실기기의 보안 저장·재실행 검증과 새 APK 빌드는 아직 수행하지 않았다.
- 로그인 요청 제한과 비밀번호 재설정 메일, 신규 iOS 플랫폼 생성·Keychain 설정은 아직 후속 작업이다.
