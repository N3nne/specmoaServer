# 사용자별 추천 데이터 준비: 서버 1단계

작성일: 2026-10-26

## 구현 범위

희망 직무를 사용자별로 저장하고, 현재 등록한 8종 스펙을 서버 내부의 분석용 데이터로 정리한다.
화면을 새로 만들거나 실제 사용자 스펙을 Gemini에 보내는 단계는 아니다.

- Stitch `specmoa.zip_ui_2` 목록과 마이 원본을 확인했으나 희망 직무 입력 화면은 확인하지 못했다.
- 사용자가 입력 화면은 나중에 제공하고 서버부터 진행하도록 승인했다. Flutter 화면·비즈니스 로직은 변경하지 않았다.
- 기존 Gemini 시연은 계속 고정된 가상 프로필만 사용한다. 희망 직무·실제 스펙의 등록/수정이 현재 AI 시연 결과에 영향을 주지 않는다.
- 기존 공고 상세의 규칙 기반 조건 비교도 변경하지 않았다.

## API

모든 경로는 기존 Bearer 접근 토큰과 활성 로그인 세션이 필요하다. 사용자 ID를 요청에서 받지 않는다.
알 수 없는 본문 필드 및 쿼리 파라미터는 400으로 거절한다. 사용자 데이터 응답은 `Cache-Control: no-store`다.

| 메서드 | 경로 | 동작 |
| --- | --- | --- |
| GET | `/career/occupations` | 지원하는 내부 직무 코드 10개와 표시 이름 |
| GET | `/career/preferences` | 로그인 사용자의 희망 직무 조회 |
| PATCH | `/career/preferences` | 희망 직무 목록 전체 교체, 빈 배열은 선택 해제 |
| GET | `/career/analysis-context` | 현재 사용자 스펙의 분석용 정리 결과와 부족 정보 조회 |

저장 요청 예시:

```json
{
  "desiredOccupations": ["backend", "mobile"]
}
```

선택 해제 요청:

```json
{
  "desiredOccupations": []
}
```

전송 형식의 `desiredOccupations` 배열은 필요하지만 사용자가 직무를 반드시 선택해야 하는 것은 아니다.
직무의 순서를 보존하고, 중복·미지원 코드·null·문자열은 거절한다. 현재 코드 목록 전체까지 선택할 수 있다.

지원 코드: `backend`, `frontend`, `mobile`, `data`, `design`, `marketing`, `accounting`, `electrical`, `safety`, `mechanical`.
이는 현재 앱의 내부 분류이며 고용24 등 공식 직업 분류가 아니다. 실제 API 도입 시 제공처 코드와 명시적으로 매핑한다.

설정 응답의 상태:

- `unset`: 아직 저장하지 않았거나 사용자가 선택을 해제했다.
- `set`: 지원하는 직무 선택이 저장되어 있다.
- `needs_review`: 이전 저장값의 버전/형식이 해석되지 않는다. 원문을 반환하거나 직무를 추정하지 않는다.

## 저장 방식

- 기존 `user_profiles.preferences` JSONB의 `career` 키를 사용한다. 새 테이블·컬럼·마이그레이션은 추가하지 않았다.
- `career` 안에 `career-preferences-v1`, 직무 코드 배열, 설정 수정 시각을 저장한다.
- 프로필이 없을 때만 첫 저장에서 생성한다. 조회는 DB에 쓰지 않는다.
- PostgreSQL `ON CONFLICT ("userId")`로 최초 동시 저장을 처리하고, JSONB 병합으로 다른 설정·프로필 필드를 보존한다.
- 분석 결과는 별도 테이블이나 캐시에 저장하지 않는다. 매번 현재 사용자의 `user_specs`를 읽으므로 삭제된 스펙이나 이전 본문이 남지 않는다.
- 기존 `user_profiles`의 사용자별 고유 관계와 기본 스키마가 존재해야 한다. 운영 배포의 기본 스키마 점검은 별도 수행한다.

## 분석 데이터 규칙

정리 버전은 `career-context-v1`이다. 각 항목은 `specId`, 스펙 종류, 원본 수정 시각, `data.action` 같은 필드 경로를 보존한다.
원본 DB 데이터는 변경하지 않는다. 전체 8종을 읽으며 목록 화면의 페이지 크기로 자르지 않는다.

| 종류 | 정리하는 주요 정보 |
| --- | --- |
| 자격증 | 명칭, 발급기관, 취득일, 입력 성적/등급, 명시한 유효기간, 키워드 |
| 어학 | 시험명, 점수/등급, 응시일, 발급기관 |
| 학력 | 학적, 학위, 학교/전공, 추가 전공, 입력한 만점 기준과 GPA |
| 수상 | 수상명, 주최기관, 상격, 수상일, 참여 형태/역할, 기여 내용 |
| 프로젝트 | 명칭, 종류, 기간/진행 여부, 역할/팀 규모, 실제 STAR 4개 항목, 기술 |
| 경력 | 회사, 고용 형태, 부서/역할, 기간/재직 여부, 업무/성과/문제 해결 내용 |
| 대외활동 | 명칭, 주관기관, 종류, 기간/진행 여부, 역할/활동 내용/수상 |
| 교육 | 과정, 기관, 종류, 교육 시간/기간, 기술, 학습 내용/프로젝트 역할 |

점수·등급·키워드는 사용자가 제공한 값만 정리한다. 시험별 임의 환산, 자동 유효기간, 경력의 임의 합산, 공식 인증, 합격률/확률은 만들지 않는다.
프로젝트는 실제 저장 구조의 `situation`, `task`, `action`, `result`를 사용한다. 가상 AI 시연의 `description` 구조로 덮어쓰지 않는다.

항목별 상태는 입력 데이터의 해석 가능성을 뜻한다. 스펙 평가 점수나 지원 자격 판정이 아니다.

- `empty`: 해석 가능한 분석 필드가 없다.
- `partial`: 최소 문맥이 부족하거나 값/기간을 재확인해야 한다.
- `available`: 해당 종류의 최소 문맥이 있다. 모든 채용 조건을 비교할 수 있거나 공식 검증된 상태라는 뜻은 아니다.
- `unsupported`: 지원하지 않는 종류의 기존 레코드다. 내용을 분석에 포함하지 않는다.

최소 문맥:

- 자격증: 명칭.
- 어학: 시험명과 점수/등급 중 하나.
- 학력: 학위와 학적 상태.
- 수상: 명칭과 상격/기여/역할 중 하나.
- 프로젝트: 명칭과 기술/역할/STAR 중 하나.
- 경력: 회사와 역할/업무/성과/문제 해결 중 하나.
- 대외활동: 명칭과 역할/활동 내용 중 하나.
- 교육: 과정명과 기술/학습 내용 중 하나.

`missingFields`는 비어 있는 선택 필드 목록이다. 필수 입력으로 변경하지 않는다.
`missingContext`는 최소 문맥에서 빠진 필드 그룹으로, 한 그룹 안에서는 하나만 있어도 된다.
`issues`는 원문 없이 문제 필드와 이유 코드만 반환한다.

- 시험명이 없으면 어학 점수·등급은 `missing_context`로 분석 사실에서 제외한다.
- GPA 만점 기준이 없으면 GPA를 환산하지 않고 `missing_context`로 제외한다.
- 잘못된 날짜·형식·점수 범위, 앞뒤가 뒤바뀐 기간은 해당 사실에서 제외한다. 다른 정상 필드는 유지한다.
- `0`점과 `false`는 누락값으로 취급하지 않는다.
- 진행 중·평생 유효·추가 전공 없음에 해당하면 비활성 필드는 누락 정보에서 제외한다.
- 자격증 번호·응시번호·공식 목록 연결 ID·알림 설정·URL 및 알 수 없는 필드는 분석에 포함하지 않는다.
- 모든 항목의 인증 상태는 계속 `unverified`다.

## 외부 AI와의 경계

`CareerModule`은 프로필/스펙 저장소만 사용한다. `AiModule`이나 Gemini 클라이언트를 주입하지 않는다.
응답의 `privacy.mode`는 `server_only`, `externalAiTransmissionAllowed`는 항상 `false`다.
이는 서버 내부 전처리라는 뜻이며 휴대폰 내부 AI 실행을 뜻하지 않는다. 배포 후에는 해당 앱 서버에서 처리한다.

번호와 URL을 제외해도 프로젝트 본문·학교·회사·활동 내용 등에 개인정보가 남을 수 있다.
익명화 완료나 외부 전송 동의 완료라고 간주하지 않는다. 분석 결과의 원문을 로그·별도 파일에 기록하지 않는다.
요청 본문에 동의 여부나 전송 허용 값을 넣어도 받을 수 없다.

실제 사용자 추천을 활성화하려면 별도 작업이 필요하다:

1. 희망 직무 입력/수정 Stitch 원본을 받아 해당 화면 연결.
2. 실제 사용자 데이터의 외부 AI 전송 범위·고지/동의·보관/삭제·사용할 서비스 정책 확정.
3. 별도 승인된 사용자 추천 경로에 입력 분량 제한·근거 검증·요청 제한 적용.
4. 운영 DB/Render와 새 앱을 함께 검증·배포. 기존 APK에는 이번 서버 개발이 자동 포함되지 않는다.

## 검증

- `npm run build`.
- `RUN_DB_TESTS=true npm test`: 62개 테스트 통과, 건너뛴 테스트 없음.
- 직무 코드·중복·초기값/해제·이전 버전 설정, 8종 선택 입력, STAR 경로, 누락값·잘못된 값·조건부 필드·원본 추적 테스트.
- 무인증/위조 토큰·사용자 ID 위조, 계정 간 격리, 동시 최초 저장, 타 설정 보존, DB 재조회, 수정/삭제 후 재조회 테스트.
- Gemini 설정이 있어도 분석 준비 과정에서 외부 HTTP 호출이 0회인지 검증.
- 실제 PostgreSQL 검증은 매번 임의 이름의 격리 로컬 테스트 DB에서 수행한 후 해당 DB만 삭제했다. 기존 개발 데이터는 수정하지 않았다.
- 기존 AI 시연·공고 조회/조건 비교·스펙 CRUD·인증·학습 기록의 서버 회귀 테스트를 포함했다.
- Flutter 파일 변경이 없으므로 이번 작업에서는 Flutter 실행/시각 비교 및 새 APK 빌드를 수행하지 않았다.
- Supabase·Render·GitHub에는 배포하지 않았다.

## Flutter 연결 준비 후속 작업 (2026-10-26)

- `ui/lib/models/career_data.dart`에 직무 목록·선택 설정·8종 분석 결과 모델을 추가했다.
- `ui/lib/services/career_api_client.dart`에서 위 4개 API를 호출한다. 사용자 ID나 실제 스펙을 요청 본문에 넣거나 Gemini 경로를 호출하지 않는다.
- 기존 `AuthenticatedClient`의 Bearer 인증·한 번의 토큰 갱신·계정 변경 후 이전 응답 차단을 재사용한다.
- 한국어 UTF-8, 빈 선택, 0/false, 원본 필드 경로, 미지원 종류를 보존한다. 반환 목록은 중첩 목록까지 수정 불가능하다.
- 버전·상태·집계·원본 경로·허용 필드·개인정보 처리 경계가 맞지 않으면 오류로 처리한다. 실패를 '스펙 0개'로 바꾸지 않는다.
- 저장 응답이 요청한 직무 선택과 다르면 성공으로 간주하지 않는다. 타임아웃·인증·구형 서버·서버 장애는 고정 메시지로 구분하고 원격 오류 원문은 노출하지 않는다.
- 응답을 캐시·기기 저장소·파일에 저장하지 않는다. 현재 화면에 이 코드를 연결하거나 사용자 입력 UI를 새로 만들지는 않았다.
- 저장된 설정 시각은 서버/클라이언트 모두 정규 UTC ISO 형식으로 확인한다. 이상한 이전 값은 `needs_review`다.

후속 검증: 서버 빌드 및 62개 테스트, Flutter 120개 테스트, Flutter 정적 분석 통과.
격리된 PostgreSQL의 Nest HTTP 응답을 가상 데이터로 출력하고 Dart 모델로 읽어 10개 직무·8종 전체 필드·수정/삭제 반영을 교차 검증했다.
실제 사용자 데이터나 Gemini 요청은 사용하지 않았다. 화면 수정/시각 비교·네이티브 빌드·배포는 수행하지 않았다.

다음 재개 위치와 실행 명령은 `docs/development_handoff.md`에 기록했다.
