# 채용공고 샘플 데이터와 API 전환 안내

작성일: 2026-10-22

## 현재 적용 범위

사람인 이용 승인 전에도 개발을 진행하기 위해 완전히 가상의 채용공고 40개를 생성해 로컬 PostgreSQL `public.job_postings`에 저장했다. 실제 채용공고나 합격자의 개인정보를 수집·복제하지 않았으며, 기존 사용자·스펙·학습 기록을 수정하지 않았다.

진행 순서는 공통 데이터 계약, 가상 공급자, 저장·검색 API, 조건 비교, 격리 DB 테스트, 로컬 적용이다. Flutter 탐색 화면은 아직 기존 자격증 검색 화면이며 이번 작업에서 변경하지 않았다. 취업 탐색 UI 연결은 해당 Stitch 원본 확인 후 별도 진행한다.

## 교체 구조

```text
현재: DemoJobSource -----------+
                              |
추후: 승인된 API의 어댑터 -----+--> JobFeedItem --> importJobs --> job_postings
                                                                  |
                                       Flutter <-- /jobs API <----+
                                                   |
                                 /jobs/:id/match <-- 현재 사용자의 user_specs
```

- `server/src/jobs/job.types.ts`: 공급자 독립적인 `JobFeedItem` 및 `JobSource` 계약.
- `server/src/jobs/providers/demo-job.source.ts`: 가상 데이터 생성기. 동일 기준일에는 동일 내용을 생성한다.
- `server/src/jobs/providers/job-source.factory.ts`: 서버에서 사용할 공급자 선택.
- `server/src/jobs/job-import.ts`: 입력 검증과 출처별 upsert. 임의의 외부 필드로 내부 ID나 출처를 덮어쓸 수 없다.
- `server/src/jobs/jobs.service.ts`: 출처가 바뀌어도 유지할 검색·필터·상세 응답.
- `server/src/jobs/job-match.ts`: 사용자별 등록 정보와 공고 조건의 참고 비교. 학습된 AI 모델이나 합격 확률 계산기가 아니다.

`source + externalId`를 중복 기준으로 사용한다. 같은 데이터를 다시 넣어도 새 공고가 계속 늘어나지 않고 내부 UUID가 유지된다. 다른 공급자가 같은 외부 번호를 사용해도 서로 덮어쓰지 않는다. 실제 API가 빠뜨린 기존 공고를 자동 삭제하거나 마감으로 바꾸지는 않는다. 실제 연동 때 공급자의 변경·삭제 정책을 확인해야 한다.

## 생성한 데이터

가상 기업명은 모두 `스펙모아 가상기업 01`과 같은 형식이고 제목에는 `[가상 공고]`가 붙는다. 데이터셋 버전은 `specmoa-demo-v1`이다.

| 직무 코드 | 직무 | 공고 수 |
|---|---|---:|
| backend | 백엔드 개발 | 4 |
| frontend | 프론트엔드 개발 | 4 |
| mobile | 모바일 앱 개발 | 4 |
| data | 데이터 분석 | 4 |
| design | UX/UI 디자인 | 4 |
| marketing | 디지털 마케팅 | 4 |
| accounting | 회계·재무 | 4 |
| electrical | 전기설비 관리 | 4 |
| safety | 산업안전 관리 | 4 |
| mechanical | 기계설계 | 4 |

직무 코드는 테스트용 자체 코드이며 사람인 공식 코드라고 간주하지 않는다. 지역은 서울·경기·부산·대전·대구·광주·인천·울산 8개다. 각 직무별 정규직 신입·인턴·정규직 경력·계약직 시나리오가 있다.

2026-10-22 한국 날짜 기준 초기 구성:

- 모집 중 35개, 마감 4개, 접수 예정 1개.
- 마감일이 없는 공고 10개. 임의의 마감일을 채워 넣지 않는다.
- 본문과 상세 요구조건이 없는 공고 10개. 실제 API의 누락 필드를 테스트하기 위한 시나리오다.
- 가상 공고는 `synthetic=true`, 안내 문구, `sourceUrl=null`, `canApply=false`로 반환한다.
- 합격자 스펙, 합격 결과, 기업별 실제 통계는 만들지 않았다.

기간은 시드 실행 시 지정한 한국 기준일로 한 번 계산해 DB에 저장한다. 조회할 때마다 날짜를 이동시키지 않으므로 시간이 흐르면 실제로 마감 상태가 된다. 시연 기준일을 갱신하려면 시드를 명시적으로 다시 실행한다. 이때 기존 가상 공고의 게시·접수·마감일이 함께 갱신된다.

## 실행 및 재생성

```powershell
cd C:\app_project\server
$env:DB_SYNC = 'false'
npm run db:migrate
npm run jobs:seed -- 2026-10-22
$env:JOBS_SOURCE = 'demo'
$env:PORT = '3101'
npm run start:dev
```

`npm run jobs:seed`처럼 날짜를 생략하면 실행 시점의 한국 날짜를 사용한다. 잘못된 날짜는 거부한다. 시드 명령은 로컬 개발 DB에서만 실행할 수 있고 운영·원격 DB에는 샘플을 자동 주입하지 않는다. 마이그레이션이나 앱 부팅만으로 데이터가 생성되지 않는다.

`JOBS_SOURCE`를 생략한 개발 환경은 `demo`, 운영 환경은 `disabled`다. `disabled`에서는 기존 가상 공고를 노출하지 않는다. 운영 시연에서 가상 데이터를 노출하려면 별도의 검토와 명시적인 설정이 필요하다. `saramin`처럼 아직 구현하지 않은 공급자를 지정하면 서버가 오류를 내고 중단하며 샘플로 몰래 대체하지 않는다.

## 서버 API

모든 경로는 현재 로그인한 사용자의 Bearer 접근 토큰이 필요하다. 공고 생성·데이터 주입용 공개 HTTP API는 만들지 않았다.

| 요청 | 기능 |
|---|---|
| `GET /jobs` | 기본 모집 중 공고 목록, 최신순, 20개 |
| `GET /jobs?occupation=backend&region=서울` | 직무·지역 필터 |
| `GET /jobs?employmentType=intern&experienceLevel=entry` | 고용형태·경력 조건 필터 |
| `GET /jobs?educationLevel=bachelor` | 공고에 기재한 학력 조건의 정확한 분류로 필터 |
| `GET /jobs?q=NestJS&sort=deadline` | 기업명·제목·키워드 검색 및 마감일순 정렬 |
| `GET /jobs?status=all&limit=40` | 마감·접수 예정까지 포함한 전체 샘플 |
| `GET /jobs?limit=10&offset=10` | 페이지 조회 |
| `GET /jobs/facets?status=all` | 필터용 항목과 각 항목의 공고 개수 |
| `GET /jobs/:id` | 해당 내부 UUID의 상세 데이터 |
| `GET /jobs/:id/match` | 현재 로그인한 사용자의 스펙과 조건 비교 |

`status`는 `open`, `closed`, `upcoming`, `all`, `sort`는 `latest`, `deadline`이다. `limit`은 1~100, `offset`은 0~100000이다. 동일 정렬 값에서는 내부 ID로 순서를 고정한다. 마감일순의 날짜 미상 공고는 뒤로 보낸다.

필터는 조합하면 모두 만족하는 결과를 반환한다. `facets`에도 동일 필터와 기본 모집 중 조건을 적용하며 `limit`·`offset`은 집계 범위를 줄이지 않는다. 사용자별 추천 순위·스크랩·지원 이력·실제 지원 접수는 이번 범위가 아니다.

## 조건 비교 정책

결과는 퍼센트 대신 조건별 상태·판단 이유·근거 스펙 ID로 제공한다.

| 상태 | 의미 |
|---|---|
| confirmed | 등록한 정보에서 해당 비교 조건을 확인함. 공식 검증 완료를 의미하지 않음 |
| not_confirmed | 입력된 학력·성적이 비교 기준에 이르지 않음. 지원 불가 판정은 아님 |
| unknown | 자료가 없거나 확정할 수 없음. 부족한 스펙으로 단정하지 않음 |
| not_required | 공고에서 학력·경력 무관을 명시함 |

- 필수 조건과 우대 조건의 집계를 분리한다. 우대 항목의 부재로 필수 조건 실패를 만들지 않는다.
- 졸업한 학위의 서열을 단순 비교한다. 졸업예정·재학은 공고의 허용 여부가 없어 자동으로 졸업과 동등하게 취급하지 않는다.
- 경력은 정규직·계약직의 월 단위 등록 기간에서 완전히 포함되는 달만 보수적으로 합친다. 겹치는 기간을 중복 계산하지 않는다. 인턴 인정이나 신입 여부는 임의로 추론하지 않는다. 기업의 실제 경력 인정과 동일하다는 보장은 없다.
- 기술·키워드는 대소문자·공백을 정규화한 정확한 일치만 사용한다. `JavaScript`를 `Java` 보유로 오판하지 않는다. 동의어·직무 유사도·서술형 경험 분석은 후속 범위다.
- 자격증은 명칭 일치에 더해 취득일과 평생 유효 또는 입력한 유효기간이 확인되는 경우만 확인으로 표시한다. 유효기간 정보가 없다고 임의로 영구 자격증이라고 판단하지 않는다.
- 어학은 등록 점수만 비교하고 유효기간 미판정을 명시한다. 시험별 유효기간이나 공식 검증을 만들어내지 않는다.
- GPA 환산, 대학·기업 서열, 성별·나이 가중치, 가상 합격 확률은 사용하지 않는다.
- 현재 사용자의 `user_specs`만 읽고, 응답에는 그 사용자의 근거 ID만 포함한다. 다른 사용자 ID를 보내도 조회 대상을 바꿀 수 없다.

### 조건 비교 보강 (2026-10-25)

`GET /jobs/:id/match`의 비교 방법을 `rules-v2`로 구분한다. 기존 상태값·필수/우대 집계·근거 ID 필드는 유지하고 다음 필드를 추가했다.

| 필드 | 내용 |
|---|---|
| `comparison.comparedAt` | 비교 기준 시각의 UTC ISO 문자열. 자격증 일자와 경력 월은 이 시각의 한국 날짜로 비교한다. |
| `checks[].reasonCode` | 판단 이유를 식별하는 코드. 상태를 대신하지 않는다. |
| `checks[].reason` | 사용자가 이해할 수 있는 한국어 설명. 공식 검증이나 합격 가능성을 뜻하지 않는다. |
| `checks[].evidenceSpecIds` | 판단에 실제 사용하거나 참고한 현재 사용자의 스펙 ID. 확인 불가·기준 미달에도 근거가 있을 수 있으므로 ID 존재만으로 충족을 판단하지 않는다. |

판단 이유 코드는 `condition_not_required`, `condition_missing`, `evidence_missing`, `evidence_incomplete`,
`minimum_met`, `below_minimum`, `certificate_validity_unconfirmed`, `experience_policy_unspecified`,
`language_exam_ambiguous`, `exact_keyword_match`다. 서버가 제공한 `status`를 기준으로 상태를 표시하고 `reason`을 설명으로 사용한다.

보강한 세부 정책:

- 모든 스펙 입력은 계속 선택 항목이다. 빈 스펙, 알 수 없는 학위, 누락된 성적을 미충족으로 처리하지 않는다.
- 학력은 졸업 학위를 비교한다. 입력된 모든 졸업 학위가 최소 기준보다 낮으면 해당 ID와 함께 `not_confirmed`를 반환한다. 다른 학력에 재학·졸업예정·학위 누락이 있으면 `unknown`을 유지한다.
- 자격증 명칭은 정규화한 정확한 일치만 인정한다. 실제 달력 날짜, 취득일이 기준일 이전인지, 평생 유효 또는 입력된 만료일이 기준일을 포함하는지 확인한다. 유효기간 미입력·만료·잘못된 날짜는 `unknown`이며 기업의 별도 인정이나 연장을 추정하지 않는다.
- 어학은 같은 시험의 숫자 점수만 비교한다. 응시일을 생략한 경우 점수만 비교할 수 있지만 입력한 응시일이 잘못됐거나 미래이면 해당 성적은 사용하지 않는다. 성적의 공식 유효기간은 여전히 미판정이다.
- 같은 시험에 최소 기준 이상인 점수가 있으면 `confirmed`, 비교 가능한 점수가 모두 낮으면 해당 ID와 함께 `not_confirmed`다. 같은 시험에 점수 누락·비교 불가 기록이 섞이고 충족 점수가 없으면 `unknown`이다.
- 숫자로 환산할 규칙이 없는 등급형 조건과 시험명이 `기타`인 항목은 `unknown`이다. OPIc 등급을 임의 점수로 바꾸지 않는다. TOEIC 990점 초과 등 기존 입력 정책상 유효하지 않은 값도 근거로 사용하지 않는다.
- 경력은 기존 보수적 월 계산을 유지한다. 완전히 포함되는 달이 없는 기간·잘못된 기간·미래 시작·인턴은 합산하지 않는다. 같은 달을 중복 계산하지 않고, 합산 기간을 실제로 늘린 기록만 경력 근거에 포함한다. 기간이 짧아도 전체 경력이 등록됐다는 보장이 없으므로 `unknown`이다.
- 현재 사용자의 스펙을 매 요청 다시 읽으므로 등록·수정·삭제 결과를 다음 비교 요청에서 반영한다. 공고 상태와 조건 비교는 하나의 기준 시각을 사용한다.

검증:

- `npm run build`: 통과.
- `RUN_DB_TESTS=true npm test`: 40개 통과, 건너뛴 테스트 없음.
- 기존 비교 정책 회귀 테스트와 함께 판단 이유·집계, 선택 입력, 낮은 학력·점수의 근거, 잘못된 날짜, 한국 자정·월 경계, 중복 경력 및 사용자 분리를 검증했다.
- 실제 PostgreSQL의 별도 임시 테스트 DB에서 학력·어학 수정과 삭제, 자격증 등록, 경력 등록과 삭제 후 비교 결과 변화를 확인했다. 임시 DB는 테스트 종료 시 정리했다.
- Flutter 화면·운영 데이터·DB 스키마·외부 API·Render·APK는 변경하지 않았다. 화면에서 비교 결과를 표시하는 작업은 별도 원본 확정 후 진행한다.

## 실제 API 승인 후 교체

1. 실제 응답을 받은 뒤 `JobSource`를 구현하는 별도 어댑터를 만든다. 샘플 생성기를 수정해서 실제 응답처럼 꾸미지 않는다.
2. 기업명·공고명·직무·지역·학력·경력·마감일 등을 `JobFeedItem`으로 변환하고 공식 코드와 자체 분류를 매핑한다. 현재 단일 직무·지역·고용형태 모델로 표현하기 어려운 복수 조건은 실제 응답을 확인한 뒤 명시적으로 모델을 확장해야 하며 임의로 버리지 않는다.
3. 제공하지 않는 공고 본문과 자격증·어학 상세 조건은 `null`로 둔다. API 필드 미제공과 조건 없음은 다르다. 현재의 사람인 공개 명세에는 본문 전체·구조화된 상세 요구조건 필드가 없으므로 가상 데이터와 동일한 세밀한 비교를 보장하지 않는다.
4. 이용 승인을 받은 서비스 범위·DB 저장/캐시 허용 범위·출처 표시·호출 한도를 확인한다. 인증키는 서버 환경변수로만 관리한다.
5. 수집 작업을 `importJobs`에 연결하고 공급자 팩토리에 등록한 뒤 `JOBS_SOURCE`를 실제 공급자로 바꾼다. 공급자별 데이터를 혼합하지 않으므로 기존 샘플 행을 먼저 삭제할 필요는 없다.
6. 공고 종료·수정 반영 정책과 호출 실패 시 최신성 표시를 검증한다. `fetchedAt`은 수집 시점이지 현재 유효함을 보증하는 값이 아니다.

API 키만 넣으면 실제 연동이 자동 완성되는 상태는 아니다. 응답 매핑과 운영 수집 정책은 남아 있지만 Flutter가 공급자 고유 응답에 의존하지 않도록 조회 형식을 분리했다.

- 충족·기준 미달·확인 불가·제한 없음과 필수/우대 집계를 실제 API 응답으로 표시한다. 조건 행을 누르면 서버가 반환한 판단 이유가 펼쳐진다.
- 원본 배지의 28px 높이, 조건 행의 40px 최소 높이와 8px 간격을 맞췄다. 작은 화면에서는 숫자와 단위가 따로 줄바꿈되지 않도록 상태별 문구를 묶었다.
- 하단 기존 코칭 상자는 실제 비교 안내·한국 시간의 비교 시각·다시 비교 동작에 사용한다. 자소서 생성은 추가하지 않았다.
- `JobApiClient.fetchComparison`은 인증 클라이언트로 `GET /jobs/:id/match`를 호출하며 사용자 ID를 쿼리로 전송하지 않는다.
- 새 모델은 `rules-v2` 응답, 상태값·판단 이유·근거 ID·기준 시각을 읽는다. 상태별 집계가 실제 항목 및 필수/우대 구분과 다르면 정상 비교 결과로 표시하지 않는다. 알 수 없는 상태나 구형 응답을 성공·실패·0건으로 추정하지 않는다.
- 공고 조회와 조건 비교를 분리했다. 비교가 늦거나 실패해도 공고·지원 링크는 유지하며 비교만 재시도할 수 있다.
- 재조회 중에는 마지막 비교 결과와 카드 크기를 유지하고 버튼을 잠시 비활성화한다. 재조회 실패는 기존 결과의 비교 시각과 오류를 함께 남긴다.
- 공고·계정·인증 세대가 바뀌면 이전 비동기 응답을 반영하지 않는다. 성공한 비교 응답의 공고 스냅샷을 사용해 조건과 본문 정보가 어긋나지 않게 한다.
- 상세 필터·스크랩·자소서 탭은 계속 제외하며 다른 화면의 디자인은 변경하지 않았다.

## Gemini 개발용 시연 서버 (2026-10-26)

- 가상 프로필과 가상 공고만 사용하는 별도 Gemini 추천 모듈을 추가했다. 기존 `rules-v2` 비교와 Flutter 화면은 변경하지 않았다.
- 실제 사용자 스펙은 읽거나 전송하지 않는다. 개발용 HTTP API도 명시적 활성화가 필요하며 운영 환경에서는 차단한다.
- 실행 방법·데이터 사용 제한·캐시·호출 제한·검증 결과는 `docs/gemini_ai_prototype.md`에 정리했다.
- Nest 빌드와 PostgreSQL 통합 검증을 포함한 서버 테스트 52개는 통과했다. 키 인증/모델 목록 조회는 정상이나 최종 실제 생성 호출은 Google 503으로 실패했다. 실제 추천 생성 성공 및 앱 표시·Render·APK 반영은 아직 완료하지 않았다.

## Gemini 탐색 시연 연결 완료 (2026-10-26, 위 초기 상태 갱신)

- 탐색 원본의 AI 칩·파란 요약·가로 추천 카드를 재사용해 개발용 AI 시연을 연결했다. 최초 진입·일반 목록 새로고침은 생성 API를 호출하지 않는다.
- 정상 thoughtSignature 메타데이터를 거부하던 파서와 오류 수신 전부터 대기 시간을 계산하던 문제를 수정하고 회귀 테스트를 추가했다.
